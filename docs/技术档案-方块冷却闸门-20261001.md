# 技术档案 · 方块冷却闸门
English: `docs/技术档案-方块冷却闸门-20261001.en.md`

- **日期**：2026-10-01
- **位置**：`doom.consumable`（命名空间 `doom.consumable:block/*` · `doom.consumable:api/block_cd_*`）
- **状态**：已实现 · 已实测（核心 14 + 扩展 12 + 视觉 15 = **41 断言全绿**）· lint 通过 · 正式源已同步
- **一句话**：给「一个方块的使用」接一套冷却闸门 —— 到期放行、冷却中否决、外观可选换成另一个方块状态。

---

## 1. 目标与非目标

**目标**

1. 让**方块交互**具备冷却：同一块方块每 N 秒只能"生效"一次。
2. 与包内既有风格一致：**闸门 + 回调**（包不替使用者决定效果，只负责判定与通知）。
3. 配置与状态**跨 `/reload`、跨重启存活**。
4. 可选：冷却期间**方块自身换成另一种形态**（"看得见的冷却"）。
5. 可选：一条命令搭原型、一条命令看调试信息。

**非目标 / 做不到（都是引擎边界，见 §2）**

| 做不到 | 原因 |
|---|---|
| "根本按不动"（连交互都不发生） | 方块交互**没有"使用前钩子"**；触发器只在事后发火 |
| 给方块挂 `use_cooldown` | 冷却只有**物品组件** + **玩家侧**两处；方块没有组件系统 |
| 新增一种方块当"冷却态" | 数据包**不能注册方块** ⇒ 只能在已存在的方块状态之间切 |
| 阻止"方块自身的行为" | 箱子开了、按钮按了、拉杆翻了 —— 都发生在回调之前 |

## 2. 引擎事实与取证（1.21.6 反编译源码 + 实测）

| # | 事实 | 出处 | 对设计的影响 |
|---|---|---|---|
| E1 | 物品冷却的门在 `useItemOn` 里，只罩**物品自己的 `useOn`** | `ServerPlayerGameMode.useItemOn` 行 345 `if (!stack.isEmpty() && !player.getCooldowns().isOnCooldown(stack)) { stack.useOn(...) }` | 给方块做冷却只能"自己造"，不能指望物品冷却 |
| E2 | **方块自身交互**在门外（更早） | 同函数行 330 `BlockState.useItemOn(...)` | 冷却拦不住开箱/按钮/拉杆 |
| E3 | **空手交互**也在门外 | 同函数行 337 `BlockState.useWithoutItem(...)` | 空手路径同理 |
| E4 | `ITEM_USED_ON_BLOCK` 触发器在**物品 `useOn` 之后**发火 | 同函数行 356–357 | 用"物品右键方块"作为入口是可靠的 |
| E5 | `DEFAULT_BLOCK_USE` **确实是可用的数据驱动触发器**（空手/无交互物品右键方块时发火） | `CriteriaTriggers` + 实测（空手右键拉杆 ⇒ 计数器 +1；手上拿木棍也走这条） | 空手交互也能进闸门 |
| E6 | 触发器**不把"被交互的方块坐标"给奖励函数**（条件里的 `location` 只用于过滤） | 触发器语义 | ⇒ 必须自己用**射线**找回那个方块 |
| E7 | 冷却真正记在**玩家**身上，键 = `cooldown_group`，缺省退化成**物品 id** | `ItemCooldowns.getCooldownGroup` = `uc.cooldownGroup().orElse(ItemBuiltInRegistryKey)` | 与鱼竿禁用同源；也是那里曾经"锁一把连带锁所有杆"的原因 |
| E8 | 冷却在**使用成功完成后**才施加 | `ItemStack.applyAfterUseComponentSideEffects` → `UseCooldown.apply` | 首次用总能漏出去一次 ⇒ 包内"软否决 + 硬禁用"两层结构的原因 |
| E9 | 实体自定义 NBT 放 `data`；`marker` 实体可作为"贴在方块上的设备" | 实测 `summon marker … {Tags:[…],data:{dc:{…}}}` + `data get entity … data.dc` | 设备载体 |
| E10 | `cd_ready` 这类**整数刻**存在实体上 ⇒ 跨 `/reload`、跨重启保留 | 实测（reload 前后 `cd_ready` 逐位相同） | 不需要额外 storage 账本 |

> 附带（同批调研、与本模块相关的结论）：`Consumable.use()` 里 `consumeTicks() > 0` 决定"进入使用态"还是"当场消耗" ——
> 这就是 `consume_seconds: 0` 会让 `using_item` 不发火的原因（见 `facts.md` 同日条目）。

## 3. 架构

```
交互（物品右键 / 空手右键）
   │  两条进度：block_use.json(item_used_on_block) · block_use_empty.json(default_block_use)
   ▼
block/entry ──① 先"重新上膛"（revoke 两条进度）★ 必须在最前
            ──② 便宜门：8 格内没有设备 ⇒ return（普通世界零开销）
            ──③ 射线：anchored eyes，每 0.25 格 × 最多 20 步（≈5 格，覆盖交互距离）
                    │
                    ▼
            block/ray_step ──命中设备▼
            block/hit ──读设备 cd_ready，与 gametime 比较
                    ├─ 外部闸门 #doom.consumable:block_gate 强制否决 ⇒ deny
                    ├─ 已到期 ⇒ allow
                    └─ 冷却中 ⇒ deny
       ┌────────────┴────────────┐
       ▼                         ▼
   block/allow               block/deny
   · 写回 cd_ready=now+N*20  · 发 #on_block_denied（带剩余 tick / key）
   · cd_count +1             · 可选：设备自带 msg / sound
   · 玩家计数 dc.block_use   · 玩家计数 dc.block_denied
   · 可选：方块换成 cooling   · 可选：把方块**重按回** cooling（见 §7-4）
   · 发 #on_block_use
                    │
   到期（时间到，不依赖任何人交互）
                    ▼
   block/tick_restore（挂在 doom.consumable:tick，每 5 tick）
        └─ as @e[tag=dc.block_cd] at @s → block/restore_ready
             （自带条件：有 cd_block_ready、cd_ready>0、已到期 ⇒ 换回 ready、cd_ready=0）
```

## 4. 数据契约（设备实体 `data.dc`）

| 键 | 必填 | 含义 |
|---|---|---|
| `cd_seconds` | ✓（默认 5） | 冷却秒数 |
| `cd_ready` | ✓（初始 0） | 下次可用的**游戏刻**；0 = 随时可用 |
| `cd_key` | 建议 | 设备名；回调里从 storage `doom.consumable:ctx block.key` 读到 |
| `cd_count` | 自动 | 已激活次数（模块累加） |
| `cd_block_ready` | 可选 | 就绪形态的方块状态串，例 `minecraft:lever[face=floor,powered=false]` |
| `cd_block_cooling` | 可选 | 冷却形态的方块状态串（**写成 `minecraft:air` 就是"用后消失、到期回来"**） |
| `cd_deny_msg` / `cd_deny_sound` | 可选 | 否决时的聊天栏文本 / 音效 |

**回调侧读到的 storage**

| 键 | 何时有 | 内容 |
|---|---|---|
| `doom.consumable:ctx block.key` | 放行 / 否决 | 设备名 |
| `doom.consumable:ctx block.left` | 否决 | 剩余 tick |

## 5. 时序（tick 内的先后，实测）

1. **服务器 tick 最前面**处理交互包 ⇒ `item_used_on_block` / `default_block_use` 发火 ⇒ 奖励函数 `block/entry` 运行；
2. `entry` 用 `anchored eyes` 起射线（必须在**眼睛**，见 §7-1），逐 0.25 格找设备；
3. 命中 ⇒ `hit` 判定 ⇒ `allow`/`deny` 当场完成（写 `cd_ready`、换方块、发回调）；
4. 到了到期刻之后，由 `tick_restore`（每 5 tick）把方块换回就绪态并清零 `cd_ready`。

**注意**：`deny` 里会**再按一次冷却态** —— 因为方块自身的交互（E2/E3）可能已改掉它的状态（拉杆翻面等）。

## 7. 踩坑清单（全部实测换来，可复用）

1. **射线必须 `anchored eyes`**：`run function` 的上下文是玩家**脚底**，直接用会在几格外落到目标下方 ——
   现象是"守卫通过、命中恒 0"，极易误判成"设备没装上"。
2. **`data get entity <选择器>` 要求选择器唯一**：缺 `limit=1` 会报 `Only one entity is allowed` 直接失败
   （测试里表现为读数 NaN）⇒ 用坐标 + `distance` 或 `nbt=` 时**都要带 `limit=1`**。
3. **进度奖励里的"重新上膛"（`advancement revoke`）必须早于任何 `return`** ★ 通用纪律：
   写在早退守卫之后 ⇒ 任何一次"守卫命中"的触发都会**消耗掉成就却不重新上膛** ⇒ 该进度**此后永久失效**。
   （本模块第一版就这么写的：任意一次"附近没有设备"的方块交互都会让模块"突然全哑"。已修，并顺带加固了 `rod/catch`。)
4. **方块自身的交互会改自己的状态**（拉杆 `powered`、活板门 `open`…）⇒ 否决时**必须重按一次**冷却态，
   否则外观会说谎（显示"就绪"而逻辑仍在冷却）。
5. **移除设备不能复用"到期换回"**（那条逻辑带到期判定）⇒ 没到期就删会**永远留下冷却态**；
   所以 `remove` 用无条件的 `force_ready`。
6. **测试夹具命名/编码**：PowerShell 的 `Set-Content` / `>` 会按本地代码页写文件、把中文变成 `?`，**当场毁文件**
   ⇒ 一律用 `write`/`edit` 工具或 node 的 `fs.writeFileSync(p, s, 'utf8')`；
   JS 模板串里**不能出现反引号**（会提前结束模板，本模块开发中崩过两次）。
7. **`nbt=` 选择器对 marker 的 `data` 子树**：需要唯一性配合（见第 2 条），坐标 + `distance` 更省事。

## 8. 移植/复用到别的包

1. 复制 `function/block/*`（14 个文件）+ `advancement/block_use*.json` + 三个 `tags/function/*.json`；
2. 全局替换命名空间前缀 `doom.consumable:` → `<你的包>:`（含 `advancement revoke` 里的进度 id）；
3. 在 `<你的包>:__load__` 里建 `dc.block_use` / `dc.block_denied` 两个 dummy objective；
4. 在主 tick（`#minecraft:tick`）里加一行 `function <你的包>:block/tick_restore`；
5. 钩子标签里填你自己的效果函数（或让第三方往里填）；
6. 验收：直接跑本档案 §6 的三类用例（建议保留 `_test_block_cd_*` 脚本改命名空间后复用）。

## 9. 可选扩展（未做，按需）

| 想法 | 现成基础 |
|---|---|
| **次数上限**（用 N 次后永久失效 / 需重置） | `cd_count` 已在累加，加个 `cd_max` 判定即可 |
| **按玩家隔离的冷却** | 现在是"设备级"（所有玩家共享一个冷却）；要分人就把到期刻存进 `storage`，键 = 玩家 UUID + `cd_key` |
| **冷却进度显示** | 现有 `cd_ready` 与 `gametime` 相减即剩余；可喂 bossbar / actionbar / display 实体 |
| **"消耗方块"模式** | `cd_block_cooling: "minecraft:air"` ⇒ 用后消失、到期原地长回来 |
| **与物品冷却联动** | 给手持物品挂 `use_cooldown`（沿用 `rod/lock` 的手法）⇒ 连 E1 那条"物品 `useOn`"路径也一起拦住 |
