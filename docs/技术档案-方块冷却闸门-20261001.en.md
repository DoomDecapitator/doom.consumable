# Technical dossier · block cooldown gate

中文: `docs/技术档案-方块冷却闸门-20261001.md`

- **Date**: 2026-10-01
- **Location**: `doom.consumable` (namespace `doom.consumable:block/*` · `doom.consumable:api/block_cd_*`)
- **Status**: implemented · measured (core 14 + extension 12 + visual 15 = **41 assertions all green**) · lint passing · the official source has been synced
- **In one sentence**: wire a cooldown gate onto "the use of one block" —— allow on expiry, deny while cooling, with the appearance optionally swapable to another block state.

---

## 1. Goals and non-goals

**Goals**

1. Give **block interaction** a cooldown: the same block can only "take effect" once every N seconds.
2. Consistent with the pack's existing style: **gate + callback** (the pack does not decide the effect for the user, only the verdict and the notification).
3. Configuration and state **survive `/reload` and restart**.
4. Optional: during the cooldown **the block itself swaps to another form** ("a visible cooldown").
5. Optional: one command to set up a prototype, one command to see debug information.

**Non-goals / can't be done (all engine boundaries, see §2)**

| Can't be done | Reason |
|---|---|
| "simply can't be pressed" (not even the interaction happens) | block interaction **has no "before use hook"**; the trigger only fires afterwards |
| attach `use_cooldown` to a block | cooldowns only exist in **two places: item components** + **the player side**; blocks have no component system |
| add a new block as the "cooling state" | a datapack **cannot register blocks** ⇒ it can only switch between block states that already exist |
| prevent "the block's own behavior" | chest opened, button pressed, lever flipped —— all happen before the callback |

## 2. Engine facts and evidence (1.21.6 decompiled source + measurement)

| # | Fact | Source | Impact on the design |
|---|---|---|---|
| E1 | the item cooldown gate is inside `useItemOn` and only covers **the item's own `useOn`** | `ServerPlayerGameMode.useItemOn` line 345 `if (!stack.isEmpty() && !player.getCooldowns().isOnCooldown(stack)) { stack.useOn(...) }` | a block cooldown can only be "built by hand", not expected from item cooldowns |
| E2 | **the block's own interaction** is outside the gate (earlier) | same function line 330 `BlockState.useItemOn(...)` | the cooldown cannot stop opening chests / buttons / levers |
| E3 | **empty-hand interaction** is also outside the gate | same function line 337 `BlockState.useWithoutItem(...)` | the empty-hand path is the same |
| E4 | the `ITEM_USED_ON_BLOCK` trigger fires **after the item's `useOn`** | same function lines 356–357 | using "item right-clicks a block" as the entry point is reliable |
| E5 | `DEFAULT_BLOCK_USE` **really is a usable data-driven trigger** (fires when an empty hand / a non-interactive item right-clicks a block) | `CriteriaTriggers` + measurement (empty-hand right-click on a lever ⇒ counter +1; holding a stick also takes this path) | the empty-hand interaction can enter the gate too |
| E6 | the trigger **does not give the reward function the "interacted block's coordinates"** (the `location` in the conditions is only for filtering) | trigger semantics | ⇒ the block must be found again with a **ray** |
| E7 | the cooldown is really recorded on **the player**, keyed by `cooldown_group`, degrading to the **item id** by default | `ItemCooldowns.getCooldownGroup` = `uc.cooldownGroup().orElse(ItemBuiltInRegistryKey)` | same origin as the fishing rod disable; also why that once "locked one rod and locked them all" |
| E8 | the cooldown is applied only **after the use completes successfully** | `ItemStack.applyAfterUseComponentSideEffects` → `UseCooldown.apply` | the first use always slips through once ⇒ this is why the pack's "soft denial + hard disable" two-layer structure exists |
| E9 | entity custom NBT goes in `data`; a `marker` entity can serve as "a device stuck onto a block" | measured `summon marker … {Tags:[…],data:{dc:{…}}}` + `data get entity … data.dc` | the device carrier |
| E10 | storing an **integer tick** such as `cd_ready` on an entity ⇒ it persists across `/reload` and restart | measured (`cd_ready` identical bit for bit before and after reload) | no extra storage ledger needed |

> Aside (from the same batch of research, a conclusion relevant to this module): in `Consumable.use()`, `consumeTicks() > 0` decides whether it "enters the using state" or is "consumed on the spot" ——
> that is the reason `consume_seconds: 0` makes `using_item` not fire (see the same-day entry in `facts.md`).

## 3. Architecture

```
interaction (item right-click / empty-hand right-click)
   │  two advancements: block_use.json(item_used_on_block) · block_use_empty.json(default_block_use)
   ▼
block/entry ──① first "reload" (revoke both advancements) ★ must be at the very front
            ──② cheap gate: no device within 8 blocks ⇒ return (zero cost in an ordinary world)
            ──③ ray: anchored eyes, 0.25 blocks × at most 20 steps (≈5 blocks, covering the interaction distance)
                    │
                    ▼
            block/ray_step ──hit a device▼
            block/hit ──read the device's cd_ready, compare with gametime
                    ├─ external gate #doom.consumable:block_gate forces a denial ⇒ deny
                    ├─ expired ⇒ allow
                    └─ cooling ⇒ deny
       ┌────────────┴────────────┐
       ▼                         ▼
   block/allow               block/deny
   · write back cd_ready=now+N*20  · fire #on_block_denied (with remaining ticks / key)
   · cd_count +1             · optional: the device's own msg / sound
   · player counter dc.block_use   · player counter dc.block_denied
   · optional: swap the block to cooling   · optional: press the block **back** to cooling (see §7-4)
   · fire #on_block_use
                    │
   expiry (time runs out, no one needs to interact)
                    ▼
   block/tick_restore (mounted on doom.consumable:tick, every 5 ticks)
        └─ as @e[tag=dc.block_cd] at @s → block/restore_ready
             (self-conditioned: has cd_block_ready, cd_ready>0, expired ⇒ swap back to ready, cd_ready=0)
```

## 4. Data contract (device entity `data.dc`)

| Key | Required | Meaning |
|---|---|---|
| `cd_seconds` | ✓ (default 5) | cooldown seconds |
| `cd_ready` | ✓ (initial 0) | the **game tick** it becomes available next; 0 = available any time |
| `cd_key` | recommended | device name; read in callbacks from storage `doom.consumable:ctx block.key` |
| `cd_count` | automatic | activation count (accumulated by the module) |
| `cd_block_ready` | optional | block state string of the ready form, e.g. `minecraft:lever[face=floor,powered=false]` |
| `cd_block_cooling` | optional | block state string of the cooling form (**writing `minecraft:air` means "gone after use, back on expiry"**) |
| `cd_deny_msg` / `cd_deny_sound` | optional | chat text / sound when denied |

**Storage read on the callback side**

| Key | When present | Content |
|---|---|---|
| `doom.consumable:ctx block.key` | allow / deny | device name |
| `doom.consumable:ctx block.left` | deny | remaining ticks |

## 5. Timing (the order within a tick, measured)

1. **At the very front of the server tick** the interaction packet is processed ⇒ `item_used_on_block` / `default_block_use` fire ⇒ the reward function `block/entry` runs;
2. `entry` starts the ray with `anchored eyes` (must be at the **eyes**, see §7-1), looking for a device every 0.25 blocks;
3. on a hit ⇒ `hit` decides ⇒ `allow`/`deny` complete on the spot (write `cd_ready`, swap the block, fire callbacks);
4. after the expiry tick arrives, `tick_restore` (every 5 ticks) swaps the block back to the ready state and zeroes `cd_ready`.

**Note**: `deny` **presses the cooling state again** —— because the block's own interaction (E2/E3) may already have changed its state (a lever flipping over, etc.).

## 7. Pitfall list (all bought with measurements, reusable)

1. **the ray must be `anchored eyes`**: the context of `run function` is the player's **feet**, and used directly it lands below the target a few blocks away ——
   the symptom is "the guard passes, hits are always 0", very easily misdiagnosed as "the device was not installed".
2. **`data get entity <selector>` requires the selector to be unique**: missing `limit=1` reports `Only one entity is allowed` and fails directly
   (in tests this shows up as a NaN reading) ⇒ when using coordinates + `distance` or `nbt=` **always include `limit=1`**.
3. **the "reload" in an advancement reward (`advancement revoke`) must come before any `return`** ★ a general discipline:
   written after an early-return guard ⇒ any trigger that "hits the guard" **consumes the advancement without reloading** ⇒ that advancement **is permanently broken from then on**.
   (This module's first version was written that way: any block interaction with "no device nearby" made the module "suddenly go mute". Fixed, and `rod/catch` was hardened along the way.)
4. **the block's own interaction changes its own state** (lever `powered`, trapdoor `open`…) ⇒ on denial the cooling state **must be pressed again**,
   otherwise the appearance lies (showing "ready" while the logic is still cooling).
5. **removing a device cannot reuse "swap back on expiry"** (that logic carries an expiry check) ⇒ deleting before expiry would **leave a permanent cooling state**;
   so `remove` uses the unconditional `force_ready`.
6. **test fixture naming/encoding**: PowerShell's `Set-Content` / `>` write files using the local code page and turn Chinese into `?`, **destroying the file on the spot**
   ⇒ always use the `write`/`edit` tools or node's `fs.writeFileSync(p, s, 'utf8')`;
   **backticks must not appear** in JS template strings (they end the template early; this crashed twice during this module's development).
7. **the `nbt=` selector against a marker's `data` subtree**: needs uniqueness as a companion (see item 2); coordinates + `distance` are easier.

## 8. Porting/reusing in another pack

1. copy `function/block/*` (14 files) + `advancement/block_use*.json` + the three `tags/function/*.json`;
2. globally replace the namespace prefix `doom.consumable:` → `<your pack>:` (including the advancement ids inside `advancement revoke`);
3. create the two dummy objectives `dc.block_use` / `dc.block_denied` in `<your pack>:__load__`;
4. add one line `function <your pack>:block/tick_restore` to the main tick (`#minecraft:tick`);
5. fill your own effect functions into the hook tags (or let third parties fill them in);
6. acceptance: just run the three classes of cases from §6 of this dossier (it is recommended to keep the `_test_block_cd_*` scripts, rename the namespace, and reuse them).

## 9. Optional extensions (not done, on demand)

| Idea | Ready-made basis |
|---|---|
| **use limit** (permanently disabled after N uses / needs a reset) | `cd_count` is already accumulating; just add a `cd_max` check |
| **per-player cooldown** | currently it is "device-level" (all players share one cooldown); to split per player, store the expiry tick in `storage`, keyed by player UUID + `cd_key` |
| **cooldown progress display** | subtracting `gametime` from the existing `cd_ready` gives the remainder; can feed a bossbar / actionbar / display entity |
| **"consumed block" mode** | `cd_block_cooling: "minecraft:air"` ⇒ gone after use, grows back in place on expiry |
| **linking with item cooldown** | attach `use_cooldown` to the held item (reusing the `rod/lock` approach) ⇒ then even the path from E1, the "item `useOn`", is blocked as well |
