# doom.consumable

中文: `docs/技术手册-物品契约与实现.md`

A unified "item use" framework: **consume / place / discard / pseudo-durability bar recovery / fishing rod right-click / shooting / throwing** all live here,
declared through `minecraft:custom_data.dc` on the item; no need to modify the pack.

- Audience: map makers, other datapack authors (using this pack as a library)
- Test entry point: `/function doom.test:consumable` (reports suite by suite)
- Dependencies: `doom.library` (cache / read-write API), optionally `doom.log` (the concurrency self-check sentinel reports E201)

---

## 1. Item contract (`dc` fields)

Placed in the item component `minecraft:custom_data.dc`. For examples see `loot_table/items/*.json`.

| Field | Value | Meaning |
|---|---|---|
| `detect` | `"consume"` / `"place"` / `"shot"` / `"throw"` | **Required**: which detection chain to use (eating / block placement / shooting / throwing) |
| `type` | `"limited"` / `"infinite"` | **Required**: limited uses / infinite |
| `max_uses` / `current_uses` | int | the upper limit and used count for limited uses (paired with `max_damage` to display a durability bar, see lint C4) |
| `remainder` | item id | the item given back after depletion |
| `depleted` | `"disable"` / `"vanish"` / `"normal"` | handling after depletion (default = disable) |
| `on_use_damage` | int | damage dealt to yourself on each use |
| `recover` / `recover_ticks` | `1b` / int | pseudo-durability bar: participates in recovery / ticks needed per notch (default 10) |
| `discardable` / `discard_cooldown` | `1b` / int | droppable / drop cooldown (default 60) |
| `arrow_refund` | item id | **only `detect:"shot"`**: the ammo topped up after each shot (vanilla consumes, pack tops up = an infinity re-creation) |
| `mag` | `1b` | **only `detect:"shot"` + crossbow**: repeating magazine —— auto-reloads after firing (see §5) |

> `detect:"shot"` (bow / crossbow / trident) and `detect:"throw"` (snowball / egg / ender pearl / XP bottle)
> have **completely identical field semantics**; only the event source differs. The two chains' code structure is **line-for-line isomorphic**,
> so an author only needs to learn one.

Runtime fields (written by the pack itself, don't fill them in by hand): `resync` (slot sync stamp), `rb_cd` (per-item recovery countdown),
`rod_locked` / `shot_locked` / `throw_locked` (disable markers).

> For authors: the contract key-name audit tool is `node tools/doomtest/dc_keys.mjs` (a list of misspelled keys / contract drift).

### 1.1 Engine fact: `consume_seconds` set to 0 skips `using_item` (**this pack supports it, but the default is still 0.05**)

`minecraft:consumable.consume_seconds`'s codec uses `ExtraCodecs.NON_NEGATIVE_FLOAT` (**0 is a legal value**),
and 0 makes `Consumable.use()` take **a different branch** (source `Consumable.java`):

```java
boolean hasDuration = this.consumeTicks() > 0;          // consumeTicks() = (int)(consumeSeconds * 20)
if (hasDuration) { player.startUsingItem(hand); return InteractionResult.CONSUME; }   // enters the "using" state
else             { this.onConsume(level, player, stack); … }                          // 0 ⇒ consumed on the spot
```

⇒ **setting 0 = instant consumption** (measured: with `consume_seconds:0` a golden apple is consumed by a single click and `consume_item` fires),
but it **skips `startUsingItem`** ⇒ ① the **`using_item` trigger does not fire**; ② therefore the "pre-use snapshot" (`core/pre_save`) is not written.

**Older versions (≤2026-09-30) therefore did not support 0-second items** (the behavior was "right-click and it just disappears, no counting and no recovery"; lint rule C5 used to block it as an error).
**Supported since 2026-10-01**, by taking the snapshot as part of the consumption reward:

```mcfunction
# core/mark_consumed (reward function of consume_item)
advancement revoke @s only doom.consumable:consume
function doom.consumable:core/pre_save        # ← key: take the usage snapshot at this moment
scoreboard players set @s dc.consume_timer 1  # ← 1 tick later process_usage_wrapper handles it as usual
```

This works because the **trigger timing** was confirmed by measurement: the reward function of `consume_item` **runs before the "deduction"** —— at the moment it is called the hand
still holds **the very item that was just consumed** (`count=N` not yet decremented). So 1 tick later the difference taken by `process_usage_wrapper` (N → N-1) still holds,
and 0-second items **go down the same chain** as ordinary items. It also incidentally fixed a real bug: the snapshot is now guaranteed to come from "this consumption", and can never be mismatched
with a stale snapshot left by "a previous wind-up that did not consume" (the wrapper additionally has an `age ≤ 2` freshness guard as a fallback).

> End-to-end measurement (golden apple, a single click): `0-second limited` → `uses 3→2→1→depleted`; `0-second infinite` → written back into the hand ✓.

**This pack's convention is still to write `consume_seconds: 0.05` by default (= 1 tick)** —— the feel is almost the same, but it keeps 1 tick of **visible using state**
(both the `using_item` and `consume_item` hooks fire), and avoids others mistakenly thinking "this item is not being detected".
When you really need "no using state at all", filling in 0 is also fine; lint rule **C5** has been downgraded from `error` to `warn` (a reminder only).

> Measured comparison (golden apple, single click / 2-second hold):
> `0.0s` single click → `using_item 0 · consume_item 1` · `0.05s` single click → neither moves ·
> `0.05s` hold → `using_item 5 · consume_item 5` (once per tick).
> Note: ordinary food is not consumed when **saturation is full** (unless `can_always_eat`); use a golden apple or a potion for experiments.

## 2. Fishing rod right-click interface (created 2026-09-27; **redesigned and verified end-to-end 2026-10-01**)

### 2.1 Why a dedicated interface is needed

The vanilla fishing rod's "use" has **no** ready-made advancement trigger: `item_used_on_block` doesn't recognize it (it doesn't interact with a block),
`using_item` doesn't recognize it either (there is no "using" duration), and `consume_item` certainly doesn't (it is not a consumable).
The three tricks from the Vanilla Library's "Common Right-Click Detection" (carrot on a stick / interaction entity / the `consumable` component) are all unusable on a fishing rod:
the carrot on a stick requires first swapping to that very item, the interaction entity is a different entity, and the `consumable` component's use behavior gets
overridden by `FishingRodItem`'s own `use`.

This interface makes the fishing rod's right-click "visible" with three mutually complementing signals:

| Signal | Source | What it gives |
|---|---|---|
| ① statistic event | scoreboard `dc.rod_use` (criterion `minecraft.used:minecraft.fishing_rod`) | **only means "casting"** (source-proven: `awardStat` is only in `FishingRodItem.use`'s cast branch; the reel branch has zero statistics) |
| ② state machine | player score `dc.rod_state` (0 not cast / 1 fishing) | whether it is "fishing" right now |
| ③ bobber ownership | entity `minecraft:fishing_bobber` + in-pack tag `dc_rod_own_<UUID[0]>` | **whose** bobber this is; the moment it disappears is a "reel" (manual reel / line break / killed by an outside force all count) |

> **The 1.21.6 fishing bobber's saved data has no `Owner` field** (real-machine proof: only `Pos/Motion/UUID/Rotation/Tags/Air/…`),
> so ownership cannot be looked up through NBT; it can only be **actively stamped at cast time**: `cast_ok` writes the player's `UUID[0]` into
> `dc.rod_uid`, then stamps `dc_rod_own_<uid>` on the bobber that appeared this tick and is nearest to the player.
> The old implementation "matching via `Owner:[I;…]`" **was dead code in 1.21.6** (silent failure) and has been removed.

A successful hook (catching an item / pulling back an entity) is additionally wired to the advancement trigger `minecraft:fishing_rod_hooked`.
The rod predicate uses **subset matching** (the form proven by the source: `predicates` and `items` are **at the same level**):

```json
"rod": {
  "items": ["minecraft:fishing_rod"],
  "predicates": { "minecraft:custom_data": { "dc": { "rod": 1b } } }
}
```

> **Basis for this form (1.21.6 source, not a guess)**: the third field of `ItemPredicate.CODEC` is
> `DataComponentMatchers.CODEC.forGetter(ItemPredicate::components)` —— **without an `optionalFieldOf("components")` wrapper**,
> so `DataComponentMatchers`'s own two fields (`components` = exact whole-component match / `predicates` = partial match)
> are **flattened up to the ItemPredicate level**. The keys of `predicates` are **component predicate type ids** (such as `minecraft:custom_data`),
> and the value goes through `CustomDataPredicate.CODEC` = `NbtPredicate.CODEC` = `TagParser.LENIENT_CODEC`, i.e. **bare NBT**,
> with the semantics of **NBT subset matching** (extra keys inside `dc` still match).
> **Counter-example (will fail to parse, never write this)**: `{"components":{"predicates":{…}}}` —— `components` is a
> **exact match** mapping of "component type → value"; it would treat `predicates` as a component type name and look it up in the registry, reporting
> `Unknown registry key … data_component_type: minecraft:predicates`.
>
> The top of `rod/catch` also has an `if data … dc{rod:1b}` guard as a **double safeguard**: if the predicate is changed incorrectly it still catches it.
> During this project's 1.21.5 → 1.21.6 migration it was once silently changed incorrectly; the signature is **the feature failing entirely with no error at all**.

### 2.2 How to wire up your own fishing rod

1. Just add one field to the item: `minecraft:custom_data.dc.rod = 1b` (complete example: `loot_table/items/test_rod.json`)
2. If you need to extend it, write logic in the callback tags (see 2.6); if you need it to "not be usable", pick one of the three entry points in 2.4
3. Get a test fishing rod: `/function doom.consumable:test/give_rod`; check on the spot: `/function doom.consumable:test/probe_rod`

### 2.3 Fishing rod-specific fields

| Field | Type | Description |
|---|---|---|
| `rod` | `1b` | **Required**: marks this item as participating in the interface (without it, the interface ignores it entirely) |
| `rod_locked` | `1b` | runtime disable marker (written by `api/rod_disable`, cleared by `api/rod_enable`) |
| `rod_clear_durability` | `1b` | empty the durability (full bar) after a successful hook —— needs like "clear durability after use" only need this one field |
| `rod_button` | `1b` | **button mode**: one right-click = cast then immediately reel (fires only `on_rod_cast`, not `on_rod_reel`) —— using the rod as a "trigger item" |
| `rod_deny_message` | string | text shown when denied (red, bare text without quotes) |
| `rod_deny_sound` | string | sound id played when denied, e.g. `minecraft:block.note_block.bass` |

### 2.4 Disabling (when the rod cannot be used) —— three entry points

| Entry point | Form | Applies to |
|---|---|---|
| static list | item tag `#doom.consumable:rod_locked` | a few rods (or all of `minecraft:fishing_rod`) permanently unusable |
| dynamic switch | `api/rod_disable` / `api/rod_enable` | state follows the **item**, can be toggled at any time |
| conditional hook | function tag `#doom.consumable:rod_gate` | decide by **player state** (health, region, effects……): run `scoreboard players set #rod_deny dc.temp 1` inside to deny |

**Two lines of defense** (why it is designed this way):

- **soft denial**: vanilla has no "before use" hook, so the interface reels back the just-cast bobber **within the same server tick**
  (the player interaction packet is processed at the very front of the tick, and this logic runs late in the tick) ⇒ the player never sees the bobber and gets no product, equivalent to "not cast".
- **hard disable**: a disabled rod automatically gets `minecraft:use_cooldown` (duration `#rod_lock dc.cfg` seconds, default 10, auto-renewed on expiry)
  ⇒ vanilla blocks "use" directly and the hotbar shows a grey bar —— the player **can see** "it can't be used right now".

### 2.5 API overview (publicly usable, parameters must all be given)

| Function | Parameters | Effect |
|---|---|---|
| `doom.consumable:api/rod_durability` | `{value:<int>}` | set the held rod's `damage` (**0 = full durability**) |
| `doom.consumable:api/rod_durability_add` | `{value:<int>}` | add or subtract wear (may be negative; never below 0) |
| `doom.consumable:api/rod_disable` | — | disable the executor's held rod (writes `rod_locked` + applies cooldown) |
| `doom.consumable:api/rod_enable` | — | lift the disable (clears `rod_locked` and `use_cooldown`) |
| `doom.consumable:api/rod_reel` | — | force-reel the executor's own bobber (interrupts fishing, no callback) |
| `doom.consumable:api/rod_casting` | — | query whether the executor is fishing: result written to `#casting dc.temp` (1 = yes) |

> All of them require the **executor to be the player himself** (write-back relies on `item replace entity @s …`).
> The macro functions (the two with `{…}`) **must be given parameters**: when a parameter is missing the whole call is silently abandoned (engine behavior, pinned by this project).

### 2.6 Callback tags (third-party mount points)

| Tag | When it fires |
|---|---|
| `#doom.consumable:on_rod_cast` | cast allowed (exactly once per cast) |
| `#doom.consumable:on_rod_reel` | fishing ended and the player is still holding the rod (manual reel / line break / bobber killed by an outside force) |
| `#doom.consumable:on_rod_catch` | successful hook (catching an item / pulling back an entity) —— catch ⊂ reel: a reel also fires right after a hook |
| `#doom.consumable:on_rod_denied` | cast denied |

> `api/rod_reel` is **interrupt semantics**: it reels the bobber in but **does not fire** `on_rod_reel` (the caller knows it did it itself),
> and it does not trigger the vanilla reel side effects such as durability / drops / pulling entities.

### 2.7 Scoreboards (read-only reference / adjustable)

| Objective | Meaning |
|---|---|
| `dc.rod_use` | criterion statistic, cumulative **casts** per player (the interface's event source; reels are not counted) |
| `dc.rod_prev` | internal to the interface: the previous tick's `dc.rod_use` (don't change by hand) |
| `dc.rod_state` | 0 = not cast, 1 = fishing |
| `dc.rod_uid` | internal to the interface: the player's `UUID[0]` (the key of the ownership tag, cached at cast time) |
| `dc.rod_catch` | cumulative successful hooks |
| `#rod_lock dc.cfg` | the cooldown seconds for renewing the rod lock (default 10) |

### 2.8 Vanilla behavior and pitfalls (author-measured / official sources)

- `use_cooldown` **does work on the fishing rod** (Mojira [MC-275882](https://mojira.dev/MC-275882) reports exactly the rod's cooldown behavior),
  but it **does not block block interaction** ([MC-275796](https://mojira.dev/MC-275796)) —— irrelevant to this interface, since the rod does not interact with blocks.
- The rod only loses durability on a **reel that hooked something**; an empty reel does not (see [MC-101033](https://mojira.dev/MC-101033) for the related phenomenon);
  so rules like "one use costs a bit of durability" should be written in a callback that calls `api/rod_durability_add`.
- `fishing_rod_hooked` only fires on a **successful hook** (catching an item / pulling back an entity); an empty reel does not fire it.
- A bobber disappearing ≠ the player reeling: death / changing dimension / timeout all make it disappear. The interface handles it as "my own bobber is gone ⇒ state self-heals",
  but **as long as the player is still holding the rod at that moment** it counts as a real reel (fires `on_rod_reel`); if not holding it, it quietly resets to zero (no callback).
- `api/rod_reel` locates the bobber by the tag `dc_rod_own_<uid>` on the bobber itself (**not** the NBT `Owner` field ——
  the 1.21.6 bobber's saved data simply has no such field). The tag is applied at the moment of the cast and travels with the entity.
- Edge case: casting the bobber into an **unloaded (non-entity-tick) chunk** makes the ownership stamping miss ⇒ a one-off "phantom reel 1 tick after the cast" appears.
  A real person at view distance ≥2 won't encounter it (it is a product of the fake-player test environment).

### 2.9 References

- Vanilla Library "Common Right-Click Detection" (CR_019): <https://vanillalibrary.mcfpp.top/datapack-index/resources/dust/3/常用右键检测.html>
  —— three general right-click detection methods (carrot on a stick / interaction entity / `consumable` component), **none of which applies to the fishing rod**; reasons in 2.1.
- Official structure: the conditions of the `minecraft:fishing_rod_hooked` trigger are `entity` (the entity pulled back or the bobber),
  `item` (the caught item), `rod` (the rod used).

## 4. Block cooldown device (added 2026-10-01)

Give "one block" a use cooldown. Vanilla has no block component —— cooldowns only exist on items (the `use_cooldown` component) and on the player side,
so here a **marker entity attached to the block** serves as the device: the configuration and the expiry tick are both stored on it (surviving reload / restart).

### 4.1 Up and running in thirty seconds

1. Stand on the target block and run `function doom.consumable:api/block_cd_place` ⇒ the block gets the device;
2. After that, anyone who does a "block interaction" with it passes the gate:
   · already expired ⇒ fires `#doom.consumable:on_block_use` (third parties do the real effect here);
   · cooling ⇒ fires `#doom.consumable:on_block_denied` (read storage `doom.consumable:ctx block.left` = remaining ticks);
3. Status / ready immediately / remove: `api/block_cd_status` · `api/block_cd_reset` · `api/block_cd_remove`.

### 4.2 Device fields (the marker's `data.dc`)

| Key | Meaning |
|---|---|
| `cd_seconds` | cooldown seconds (default 5) |
| `cd_ready` | the game tick it becomes available next (0 = available any time; on allow, written back as now + seconds*20) |
| `cd_key` | device name; read in callbacks from storage `doom.consumable:ctx block.key` |
| `cd_count` | activation count (accumulated by the module, useful for observation or use limits) |
| `cd_deny_msg` / `cd_deny_sound` | optional: chat text / sound when denied |

### 4.3 Entry points and external hooks

- Entry advancements: `block_use.json` (`item_used_on_block`) + `block_use_empty.json` (`default_block_use`, covers empty hands too)
  ⇒ both point at `doom.consumable:block/entry`.
- Hooks: `#doom.consumable:block_gate` (write `#block_deny dc.temp 1` to force a denial) ·
  `#doom.consumable:on_block_use` · `#doom.consumable:on_block_denied`.

### 4.4 How to find "the block that was interacted with"

The vanilla trigger **does not give the reward function** the block coordinates (the `location` in the conditions is only used for filtering; the function cannot read it) ⇒
`block/entry` uses a ray that goes "from the **eyes** along the line of sight, advancing 0.25 blocks each time, at most 20 steps (5 blocks)" to find the device.

⚠ `anchored eyes` is mandatory: the context of `run function` is the player's **feet**, and used directly it shoots from the feet,
landing below the device a few blocks away —— measured during development (the guard passes, yet it can never hit; hits are always 0).
⚠ The ray only recognizes this pack's devices and **not walls**: a device within 5 blocks behind a wall is recognized too (this module is a "device gate", not a physical ray check).

### 4.5 Capability boundaries (an honest account)

Block interaction has no "before use hook" ⇒ **the block's own behavior has already happened** (chest opened, button pressed).
This module only does "cooldown check + callback"; whether to undo / punish / change the block state is decided by the callback.
If you want "it simply can't be pressed", that is impossible at the datapack level and can only be done through the block's own state (for example `setblock` to another block).

> Measured (2026-10-01 · 14 assertions all green): first allow on the item path (`cd_ready` differs by 61 ticks ✓, `cd_count` 1→2) ·
> interacting again while cooling is denied ✓ · allowing again after waiting 3.5 seconds ✓ · external gate forcing a denial ✓ · the empty-hand path also enters the gate ✓ ·
> `reset` / `remove` API ✓. Both entry advancements' firing was measured: `item_used_on_block` (placing a torch) and `default_block_use` (pulling a lever with an empty hand).

### 4.6 Cooling-state appearance: swapping the block directly (optional, added 2026-10-01)

A device can declare two block forms, and the module `setblock`s automatically when the cooldown starts/ends:

| Field | Meaning |
|---|---|
| `cd_block_ready` | the block state string when ready, e.g. `minecraft:lever[face=floor,powered=false]` |
| `cd_block_cooling` | the block state string while cooling, e.g. `minecraft:lever[face=floor,powered=true]` |

Timeline: allow ⇒ swap to `cooling` · expiry ⇒ `block/tick_restore` (scans the devices every 5 ticks) swaps back to `ready` ·
denied ⇒ **pressed back into `cooling`** · `api/block_cd_remove` ⇒ **unconditionally** swaps back to `ready` and then deletes the device.

⚠ Two pitfalls (measured 2026-10-01):

1. **The block's own interaction changes its own state** (lever `powered`, trapdoor `open`…) ⇒ on denial it must be pressed again,
   otherwise the appearance lies (showing "ready" while the logic is still cooling).
2. Removing a device **cannot** reuse the "swap back on expiry" logic (it carries an expiry check) ⇒ deleting before expiry would leave a permanent cooling state;
   so `api/block_cd_remove` uses `block/force_ready` (the unconditional one).

> 📄 **Technical dossier** (design · engine evidence · 41 measured assertions · pitfall list · porting guide · optional extensions):
> `docs/技术档案-方块冷却闸门-20261001.md`

### 4.7 Prototype and debugging (added 2026-10-01)

- `api/block_cd_demo` —— one command: turn [the block under your feet] into a lever + install the device (5-second cooldown + denial message).
  ① right-click ⇒ the lever flips up and the cooldown starts ② right-click again while cooling ⇒ denied (the lever is pressed back) ③ after 5 seconds it flips back automatically ④ remove it with `api/block_cd_remove`.
- `api/block_cd_debug` —— status particles on every device within 16 blocks (**green = ready / red = cooling**) + prints the totals and per-device details.
- `api/block_cd_status|reset|remove` —— one device's status / ready immediately / remove.

> **On the "alignment model"**: `item_model` / `custom_model_data` are **item** components (items use them to swap appearance);
> **blocks** have no component channel —— a block's look is determined by the resource pack's `assets/<ns>/blockstates/<block>.json` per **block state**.
> So the standard way to "swap a block's appearance for cooling" is exactly this section's form switching: pick a native block with a **boolean state** as the carrier
> (lever `powered` / copper bulb `lit` / trapdoor `open` …), and give each state its own model in the resource pack ⇒ the visuals and the logic both align.
> The datapack itself **cannot add blocks**; it can only switch between these already-existing states.

> Measured (same day · 15 assertions all green): the demo sets up with one command · right-click ⇒ the block becomes the cooling state ✓ · right-click again while cooling ⇒ denied and the block is pressed back to the cooling state ✓ ·
> after 6 seconds it returns to the ready state automatically ✓ · it can be activated again once the cooldown ends ✓ · `debug` reports no errors ✓ · `remove` swaps back to the ready state before deleting ✓.

## 5. Shot chain and throw chain (added 2026-10-05)

The two chains are **line-for-line isomorphic**; the only differences are the event source and how the item id is determined.

### 5.1 `detect:"shot"` —— bow / crossbow / trident

- **Event source**: the vanilla statistic criteria `minecraft.used:minecraft.{bow,crossbow,trident}`
  ⇒ the engine only +1s when the **projectile actually fires** (an empty draw / an undercharged draw does not increase it) ⇒ the same "stat difference" as the fishing rod chain.
- **Charge spending / write-back**: `shot/process_one` (read `current_uses` → spend 1 → write back `current_uses` and the pseudo-durability `damage`).
- **Three depletion modes**: `vanish` (default, the item disappears) / `disable` (stays in hand + `shot_locked` + a 1-hour `use_cooldown`) / `normal` (strip the `dc` and pseudo-durability components ⇒ turns back into an ordinary bow).
- **`arrow_refund`**: top up the specified ammo per shot (vanilla deducts 1, the pack adds 1 = an infinity re-creation). When the inventory is full, `give` silently fails (a known limit, no error).
- **Main hand first, offhand as fallback**: when both hands hold shot weapons, **only the main hand is processed**.
- **Callback**: `#doom.consumable:on_shot` (fires whether or not a charge was spent).

### 5.2 `dc.mag` —— infinite crossbow / repeating magazine (P0-2)

Add a `mag:1b` field to a crossbow and it **auto-reloads** after firing ⇒ semi-automatic repeating fire.

- **Implementation notes**: go through `item modify` + `item_modifier/shot_recharge.json` (`set_components` writes a fixed
  `charged_projectiles:[1 arrow]`). Because the written value is a **constant**, it can **modify the player's held item directly**,
  with **no** `item_display` relay entity —— this is the key simplification compared with `writeback` (whose value must be computed at runtime and can only go through a relay entity).
- **Double ammo supply**: `mag` refills the **crossbow's chamber** (vanilla empties `charged_projectiles` after a shot),
  `arrow_refund` refills **inventory arrows**; you need both to call it "infinite repeating fire".
- **Boundaries (asserted)**: a crossbow without `mag` **is not** reloaded; firing a crossbow's **depleting shot** does not reload either (otherwise depletion could never be reached).
- **Rate throttling**: it is recommended to attach `use_cooldown` as in `loot_table/items/repeating_crossbow.json`
  (the example is 0.25 seconds/shot ≈ 4 shots/second), and to give it a **dedicated `cooldown_group`** (otherwise it would cool down every crossbow together).

### 5.3 `detect:"throw"` —— snowball / egg / ender pearl / XP bottle (P0-1)

- **Event source**: the vanilla statistic criteria `minecraft.used:minecraft.{snowball,egg,ender_pearl,experience_bottle}`.
  > ★ **Measurement correction**: it was once thought that "vanilla has no `used:snowball` statistic and an event source must be built separately" —— **that judgement does not hold**.
  > Three real-machine proofs on this machine's 1.21.11: ① `scoreboard objectives add probe.snow minecraft.used:minecraft.snowball`
  > **creates successfully**; ② a fake player holding a snowball pressing 5 times ⇒ scoreboard **5**, inventory 16→11; ③ the control group
  > `minecraft:stick` pressed 3 times ⇒ **0** (proving it is "specific to throw semantics", not a generalized right-click counter).
  > ⇒ throwables **can reuse the structure of the shot chain directly**, with no entity detection / advancement variant needed.
  > (Ragecraft IV's `@e[type=snowball]` + tag dispatch is for **projectiles the map summons itself**;
  > those snowballs do not pass through a player throw and naturally have no stat —— a different problem from "charging a player's throw".)
- **Fields**: exactly the same as `shot` (`type` / `max_uses` / `current_uses` / `depleted`),
  but without `arrow_refund` and `mag` (a throwable has no refillable intermediary and no chamber).
- **Callback**: `#doom.consumable:on_throw`.
- **Projectiles**: `loot_table/items/{limited,infinite}_snowball.json` · `limited_ender_pearl.json`.
